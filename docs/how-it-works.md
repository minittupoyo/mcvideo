# 仕組み

生成されるデータパックは、動画の1フレームごとに2つの関数を持ちます。ここでは、設計の理由を説明します。

## 1. マーカーによる相対配置

データパックの `schedule function` で予約された関数は、元の位置や向きを引き継ぎません（ワールドの原点で実行されます）。
そのため、`fill ~ ~ ~ ...` のような相対座標は使えず、固定座標を書き込むと「置く場所が決まったパック」になってしまいます。

そこで、`<名前>:start` を実行したときに、**マーカー**（見えないエンティティ）を画面の中心に置き、以降の全フレームを、マーカー基準のローカル座標 `^左 ^上 ^前` で描きます。

```
start:  プレイヤーの位置と向きからマーカーを召喚する（タグ <名前>_o）
f/N:    execute at @n[type=marker,tag=<名前>_o] run function <名前>:d/N
        schedule function <名前>:f/(N+1) 2t           ← 次のフレームを予約
d/N:    fill ^a ^b ^ ^c ^d ^ ...                       ← マーカー基準で描く
```

- `f/N` が `at` でマーカーの位置・向きに切り替えるので、予約された関数でも、同じ場所に描けます。
- 画面は、マーカーを通り、前方に垂直な平面に置かれます（`^前` は常に 0）。
- 停止は、`#run` スコアを 0 にします。各フレームは `#run` が 1 のときだけ、次を予約します。最後のフレームは `#run` を 0 にして、止まります。

### 配置の基準（`--anchor`）

| `--anchor` | マーカーの位置 |
|---|---|
| `bottom`（標準） | 水平方向に `--dist` ブロック先、高さは「画面の下端が足元の高さ」になるように |
| `gaze` | 目線の先 `--dist` ブロックの点が、画面の中心 |

`bottom` では、`rotated ~ 0` で向きの水平成分だけを使うので、見上げて実行しても、画面の位置は変わりません。

## 2. ブロック版

### 差分書き換え

前のフレームと違うピクセルだけを書き換えます。さらに、同じ色の隣り合うピクセルを、長方形にまとめて、1つの `fill` にします（`convert.rects`）。
最初のフレームの前に、背景色（パレットの最も暗い色）で壁全体を塗ります（空気だけを置き換えます）。

### 地形を壊さない

書き換えは、`fill ... <新しい色> replace <古い色>` の形で、**直前にそこにあった色のブロックだけ**を置き換えます。
壁が地面や建物に重なっても、パレット以外のブロックは、一切変わりません（重なった部分は描かれないだけです）。
撤去（`cleanup`）も、パレットのブロックだけを空気にします。

ブロックタグ（`replace #名前:タグ`）は使いません。再現実装の Horizon では、タグ指定の `fill` が動かなかったためです。

### ストラクチャー方式（標準、`--method structure`）

`fill` の命令を大量に並べる代わりに、1フレームの変化分を、1つのストラクチャーファイル（`data/<名前>/structure/d/N.nbt`）にして、`place template` で置きます。

```
d/N:  execute if score #rot <名前> matches 0 run place template <名前>:d/N ^<左端> ^<下端> ^ none
      execute if score #rot <名前> matches 1 run place template <名前>:d/N ^<左端> ^<下端> ^ clockwise_90
      （180、counterclockwise_90 も同様。実行されるのは、`#rot` が一致する1行だけ）
```

- 関数の命令数は、1フレームあたり数百から4に減ります（変化がないフレームは0）。ファイルの合計サイズは、ほぼ同じです。
- ストラクチャーは、幅 W、高さ H、奥行き 1 で、x 軸が「左」、y 軸が「上」です。変化した画素のブロックだけを持ち、残りのマスには触れません。
- 向きは、`start` で 東西南北に丸めたときに、`#rot`（0 南、1 西、2 北、3 東）に覚えておき、`place template` の回転（`none` / `clockwise_90` / `180` / `counterclockwise_90`）に対応させます。ローカル座標 `^` で、左下の角に置きます。
- 背景は、`bg.nbt`（全面が最も暗い色）を、`start` で置きます。
- `fill ... replace <古い色>` と違い、**変化したマスの地形は上書きされます**。後片付け（`cleanup`）は、これまでどおり `fill` で、パレットのブロックだけを空気にします。
- NBT は、標準ライブラリだけで書きます（`nbt.py`）。ファイルの `DataVersion` は、`--nbt-data-version`（標準 4671）で変えられます。ゲームのバージョンと合わないときは、この値を合わせてください。
- Horizon（26.3）で、東西南北の4方向とも、壁が正しい向きで（左右反転せずに）描かれ、アニメーションすることを確認しました（`--nbt-data-version` は標準の 4671 のままで読み込めました）。Horizon、Prism の Fabulously Optimized（128x72、約194秒、`full` パレット）、バニラの 26.3 で、動作を確認しました。

### ワールドの高さ制限

`fill` は、角の座標が1つでもワールドの高さ（標準 -64〜319）の外にあると、**全体が失敗します**（「その位置はワールド外です」）。
地面付近で実行すると、壁の下半分が -64 を下回るので、`start` で、マーカーの高さを、壁が範囲内に収まる値に補正します。

### 向き

ブロックの壁は軸に沿うため、向きを東西南北の4方向に丸めます。マーカーを、ブロックの中心（`.5`）に揃えるので、ローカル座標の整数オフセットは、きれいにブロックの境界に載ります。

### パレットと減色

減色は ffmpeg の `paletteuse` に任せます。パレットは、最大256色の画像として渡します。
出力された各ピクセルの色から、パレットの番号を求めるために、**赤の値**だけを使い、256バイトの変換表（`bytes.translate`）で番号に直します。純Pythonで高速に動かすための工夫で、赤の値が重ならないよう、必要なら数ユニットずらします（`palette.unique_red`）。

ブロックの色は、ゲーム本体のテクスチャを平均して求めます（`make_palette`）。落下するブロック（砂、コンクリートパウダー）、光るブロック、時間で色が変わるブロック（銅）は避けます。銅は、蝋引き（ワックス）のものを使います。

## 3. パーティクル版

- 光らせたい画素（明るさが `--thr` 以上。`--invert` で暗い画素）ごとに、`particle dust{color:[r,g,b],scale:...} ^左 ^上 ^ 0 0 0 0 1 force` を出します。
- パーティクルは、出したあとに消せません。毎フレーム、すべて出し直すので、寿命が長い粒は残像になります。`dust` は、`scale` を小さくすると寿命が短くなります。`end_rod` は白く明るいですが、寿命が長く、残像が強く出ます。
- `dust` は、夜に暗い青みがかった色になります（その位置の明るさで色が変わるため）。そこで、画面の面に、`light` ブロック（明るさ15）を疎らに置いて、粒を明るく保ちます。光は15ブロックまで届くので、画面は地面から浮かせると、地面が照らされません（`--lift`）。
- 暗い画素（黒に近い色）は、パーティクルでは背景に溶けるため、描きません。

## 4. 音声

`ffmpeg` で `ogg`（Vorbis）に変換して、リソースパックの `sounds.json` に登録します。開始時に `playsound <名前>:video` で鳴らします。
映像はゲームの tick（標準 2tick ごとに1フレーム）で進み、音声は実時間で流れるため、ゲームが重くなると、映像が音声に遅れる可能性があります。
